# 🛠️ MVGR Reparaciones - Frontend

Sistema de gestión de reparaciones desarrollado con React, TypeScript y Vite. Aplicación web moderna y profesional para administrar clientes, equipos, reparaciones y repuestos.

## Registro con consentimiento

`VITE_REGISTRATION_CONSENT=true` habilita la lectura de condiciones y las confirmaciones explícitas
en `/register`. Requiere el GET público de requisitos publicado y el consentimiento de registro
habilitado en backend. Ausente/`false` conserva el rollout legacy; un valor inválido bloquea el registro.
El flag frontend no reemplaza el enforcement del servidor. No activarlo con borradores ni antes de
verificar la configuración y publicación en staging.

La pantalla conserva clave y payload sólo en memoria para recuperar una respuesta perdida. Cambiar
datos o revisar condiciones inicia otro intento; una versión nueva exige confirmar de nuevo.
Los documentos recibidos se muestran completos como texto seguro, sin ejecutar HTML.

Prueba de navegador del rollout activo, con servidor aislado en 5174 y API simulada:

```sh
npx playwright test --config=playwright.registration.config.ts --workers=2
```

El [plan de salida inicial](docs/plans/2026-09-08-salida-inicial-alcance-y-cierre.md) distingue esta
evidencia local del recorrido pendiente en staging con backend y PostgreSQL reales.

Prueba completa con servidor HTTP real y PostgreSQL 16 descartable:

```sh
npm run test:e2e:registration-real
```

Requiere Java 21 (`JAVA_HOME`), Docker activo, dependencias npm instaladas y el backend hermano
`../mvrg-backend`; `ORDENFIX_BACKEND_DIR` permite indicar otra ruta. El runner compila los tests y
ejecuta únicamente `LegalRegistrationBrowserE2E`. Ese harness crea la base, arranca Spring Boot
en un puerto aleatorio de loopback, ejecuta Playwright en escritorio/móvil y valida la evidencia
persistida antes de cerrar los recursos. Vite usa `127.0.0.1:5175` y no reutiliza servidores ajenos.

También recorre titular y empleados: alta de USER desde una cuenta TRIAL, login y operación con
clientes, restricciones por rol, aislamiento entre talleres y pérdida de acceso al desactivar.
Conserva los seis casos de registro y dos recorridos de empleados (escritorio y móvil 320 px).
Agrega cuatro recorridos de reparación: presupuesto aprobado o rechazado desde el seguimiento
público y entrega sin cobros, en ambos dispositivos. Usa talleres sintéticos FREE/ACTIVA para
comprobar el módulo deshabilitado y el consumo del cupo; esa preparación no prueba el vencimiento
del trial. Esas reparaciones conservan cero cobros registrados.

Otros dos recorridos comprueban el módulo opcional en TRIAL: entrega antes de registrar cobros,
carga externa manual por un USER, anulación reservada al titular y nueva carga corregida. El
historial conserva el movimiento anulado y la vista por período cuenta sólo el activo. PostgreSQL
verifica importes, pertenencia y auditoría, sin registros nuevos en las tablas de pagos del proveedor.
Son catorce casos en total. El filtro de login sigue activo con límite de 20 sólo en el laboratorio.

Este laboratorio utiliza identidades, claves y textos técnicos de prueba. No envía email ni activa
Mercado Pago; no publica borradores legales ni apunta a staging/producción. Los casos de red cortan
deliberadamente una lectura o descartan una respuesta real 201 para comprobar la recuperación.
Las respuestas de negocio y la sesión provienen del backend. La configuración de navegador exige
la URL local y el reporte del harness, por lo que no se ejecuta directamente contra una API remota.

## 🏗️ Arquitectura

### Patrón de Arquitectura

El proyecto sigue una **arquitectura modular y escalable**:

```
┌─────────────────────────────────────────┐
│           PAGES (UI Layer)              │
│  LoginPage | DashboardPage | CRUD Pages │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│      COMPONENTS (Reusable UI)           │
│  DataTable | Modal | FormField | etc.   │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│      HOOKS (Business Logic)             │
│  useQueries | useMutations              │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│      API LAYER (Data Fetching)          │
│  Axios Client | Queries | Mutations     │
└──────────────┬──────────────────────────┘
               │
┌──────────────▼──────────────────────────┐
│      STATE MANAGEMENT                   │
│  Zustand (Auth) | React Query (Server)  │
└─────────────────────────────────────────┘
```

### Flujo de Datos

1. **Usuario interactúa** → Página/Componente
2. **Componente llama** → Hook (useQuery/useMutation)
3. **Hook ejecuta** → Función de API (query/mutation)
4. **API envía** → Request HTTP (Axios)
5. **Axios intercepta** → Agrega JWT automáticamente
6. **Backend responde** → Datos
7. **React Query cachea** → Actualiza UI automáticamente

## 🔐 Autenticación

### Flujo de Login

1. Usuario ingresa credenciales en `/login`
2. React Hook Form valida con Zod
3. Se envía `POST /api/auth/login` con `{ username, password }`
4. Backend responde con `{ token, username }`
5. Token se guarda en Zustand (persistido en localStorage)
6. Redirección automática a `/dashboard`

### Protección de Rutas

```typescript
// Rutas públicas
/login

// Rutas protegidas (requieren JWT válido)
/dashboard
/clientes
/equipos
/reparaciones
/repuestos
```

### Interceptores Axios

- **Request Interceptor**: Agrega automáticamente `Authorization: Bearer <token>` a todas las peticiones
- **Response Interceptor**: Si recibe `401 Unauthorized`, hace logout automático y redirige a `/login`

**Props:**

## 💻 Desarrollo

### Estructura de un Módulo CRUD

Cada módulo (Clientes, Equipos, etc.) sigue esta estructura:

1. **Types** (`src/types/index.ts`)
   ```typescript
   export interface Entity {
     id: number;
     // campos...
   }
   
   export interface EntityCreate {
     // campos sin id...
   }
   
   export interface EntityUpdate {
     id: number;
     // campos opcionales...
   }
   ```

2. **Queries** (`src/api/queries/entity.queries.ts`)
   ```typescript
   export const useEntitiesQuery = () => {
     return useQuery({
       queryKey: ['entities'],
       queryFn: fetchEntities,
     });
   };
   ```

3. **Mutations** (`src/api/mutations/entity.mutations.ts`)
   ```typescript
   export const useCreateEntityMutation = () => {
     const queryClient = useQueryClient();
     return useMutation({
       mutationFn: createEntity,
       onSuccess: () => {
         queryClient.invalidateQueries({ queryKey: ['entities'] });
       },
     });
   };
   ```

4. **Page** (`src/pages/EntityPage.tsx`)
   - Schema de validación con Zod
   - Formulario con React Hook Form
   - Tabla con DataTable
   - Modal para crear/editar

### Agregar un Nuevo Módulo

1. Agregar tipos en `src/types/index.ts`
2. Crear queries en `src/api/queries/`
3. Crear mutations en `src/api/mutations/`
4. Crear página en `src/pages/`
5. Agregar ruta en `src/router/index.tsx`
6. Agregar item en `src/components/Sidebar.tsx`

## 🐛 Troubleshooting

### Problema: No se conecta al backend

**Solución:**
1. Verificar que el backend esté corriendo en `http://localhost:8080`
2. Verificar CORS en el backend
3. Revisar `VITE_API_BASE_URL` en `.env`
4. Revisar la consola del navegador para errores

### Problema: Token no se guarda

**Solución:**
1. Verificar que el backend devuelva `{ token, username }`
2. Revisar localStorage en DevTools
3. Verificar que Zustand esté configurado correctamente

### Problema: Rutas protegidas redirigen al login

**Solución:**
1. Verificar que el token esté guardado en localStorage
2. Verificar que el token no haya expirado
3. Revisar interceptores de Axios

### Problema: Formularios no validan

**Solución:**
1. Verificar que los schemas de Zod estén correctos
2. Verificar que React Hook Form esté configurado con `zodResolver`
3. Revisar mensajes de error en la consola
